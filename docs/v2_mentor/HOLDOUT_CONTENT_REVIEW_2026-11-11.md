## 1. 崩溃：`assign_ids` 假设"元素必属于某容器"

```
graph.py:196  c["elements"] = [e["id"] for e in graph["elements"] if e["container"] == c["id"]]
KeyError: 'container'
```

`assign_ids` 只在"元素落在某个容器内"时写 `e["container"]`，孤儿元素不写；下一行却无条件索引。前三族恰好所有元素都在容器内，所以从没触发。

## 8. 第 1 项落地记录（2026-11-11 夜，perception + emission）

### 8.1 段落丢失：不是 VLM 的锅

三层证据：

1. VLM 返回的是**完整整段**（`.vision_cache/86a44964…json`）：`bbox [238,500,1075,65]`、文本一字不差；
2. EasyOCR 也读到了（`ocr_supplement.json` observations，0.91）：第 1 行 `y=499`、第 2 行 `处理状态。` `y=545`；
3. 丢在 `merge_ocr_candidates` 的两条规则互相踩：第 1 行命中 `already-covered` 被跳过；第 2 行命中 `overlong`，把 grounding 的整段删掉，**而唯一能重建它的那一行已经被跳过**，净效果是只剩 4 个字。

`replaced_covered` 里记着这次删除，`fidelity` 仍报 pass——它只检查"清单内部有没有丢"，不检查"图上的字进没进清单"。

### 8.2 修复：分工表

| 维度 | 权威方 | 理由 |
|---|---|---|
| 文本内容 | VLM（grounding） | OCR 有标点错、断词（`访问环`/`境`）、`;` 代逗号 |
| 行几何 | OCR 行框 | VLM 不吐行框，只给整段框 |

落地为一条通用规则 `_attach_paragraph_line_groups`：**若一个元素被 ≥2 条上下堆叠的 OCR 行覆盖，且这些行拼起来与元素文本相似度 ≥0.8，则保留元素文本、把行框挂成 `measuredLines`，这些行不再单独入清单**。并排的框（表格单元格）判定为 `columns`，仍走原来的精确替换。

透传链补了三处被字段白名单吃掉的字段：`inventory`（清单）、`som/annotate`（SOM）、`fixed_canvas_compiler`（设计元素）；字号按行框反解（正文 61.75 → 25.71，右栏 56 → 22.86），不再把整块高度当一行。

### 8.3 效果

| 指标 | 修复前 | 第 1 次修（只保段） | 第 2 次修（通用行框） |
|---|---|---|---|
| critical | 17/18 | 18/18 | **18/18** |
| 正文段落 | 只剩 `处理状态。` | 两行、25.71 | 两行、25.71 |
| 右栏段落 | 一行 56px 溢出 | 一行 56px 溢出 | **两行、22.86** |
| within30 | 89.67% | 89.48% | **89.94%** |

对照图：`output/_holdout_review/compare_paragraph.png`、`compare_rightcol.png`。

### 8.4 三族是否受影响

预演（用三族落盘的 `10_pagegraph` grounding 元素 + `ocr_supplement` 观测跑新规则）：**dark / light-form / light-table 均 0 命中**。原因是它们的多行内容早已被 OCR 拆成独立元素，没有"一个元素被多条行覆盖"的形态。

为了不靠预演下结论，又跑了一次**三族全量**（`image_figma_mvp.py`，非 `--rerun`，含感知）：

| 族 | rerun（冻结感知） | full（重跑感知） | `attached_line_groups` |
|---|---|---|---|
| dark-card-grid | 94.65 / 27-27 / 1-30 | **完全一致** | 0 |
| light-table | 95.27 / 30-30 / 36-59 | **完全一致** | 0 |
| light-form | 92.21 / 24-24 / 29-33 | 91.12 / 24-24 / **19-29** | 0 |

light-form 的差异**不是这条规则造成的**（`attached=0`），而是 **VLM 重采样**：

| | 冻结感知 | 本次 full |
|---|---|---|
| grounding 文本元素 | 18 | **29** |
| OCR 追加 | 40 | 21 |
| 清单条目 | 141 | 171 |

即 `_rerun_family` docstring 里记的那个老问题——**全量跑会重新采样 VLM，结果不可与冻结跑横比**。这条对 holdout 也成立：holdout 的 before/after 之所以可比，是因为同一张图命中了同一份视觉缓存（两次感知均为 27 个元素、来源构成一致，`added` 都是 0，只有 `attached` 从 1 变 2）。

**由此得到一条该写进流程的规矩**：任何"感知改动"的 A/B 必须固定在**同一次感知产物**上做（`--rerun`），或者先确认视觉缓存命中；否则 VLM 方差（本族 within30 −1.09、native −10）会盖过被测改动的量级。

### 9.1 缺的不是发射，是"形状"这一类对象

审计过：holdout 的清单构成是 `asset 8 / text 20 / control 3`，**零个 panel、divider、progress、bar**；pagegraph 只有 4 个粗区域（banner/main/aside/footer）。所以卡片边框、进度条、标题竖条不是"发射时丢了"，是**从来没有被当作对象**。

### 9.2 三条路都试过，只有一条站得住

| 方法 | 结果 |
|---|---|
| 背景差 + 连通域 | 页面是渐变，阈值 3–6 时整张图连成一块，分不开 |
| 1px 边框线配对 | 卡片边框上下的邻居本身不同（白/灰），"两侧相等"过严；放宽后渐变噪声全成线 |
| 洪泛填充 | `tol=1` 能精确切出卡片（`[246,647,269,114]`），但 `tol≥5` 漏满全图；且每个嵌套盒都要重新播种 |
| **量化颜色 + 连通分量** | **一次扫描分开主面板与三张卡**（卡边框量化成另一个值，天然把白卡从白页里切出来），0.2s |

最终实现 `src/app/services/structure/fidelity/decoration_pixels.py`：

- `panels()`：量化 → 取最常见的 16 种颜色 → 各自连通分量 → 过滤（面积、填充率、不贴画布边）→ **小于画布 2% 的面板必须压住内容**（滤掉渐变产生的 ~50px 瓦片）；
- `solid_blocks()`：饱和色连通块，要求**短轴方向真的恒定**（在 2px 内缩后测），否则蓝字闭合成块会被误当条形；
- `page_background()`：**"所有元素之外还剩什么颜色"**——旧值是图像主色，卡片一大就变成卡片色，页面底色因此丢失；
- `panel_decorations() / solid_decorations()`：输出 `rectangle`，按面积降序，压在所有叶子之前。

## 10. §6.3 反色：不是调色板错，是 fill/ink 互换（2026-11-12 凌晨）

### 10.1 真实机制

交接文档写的是"默认调色板问题"，实测不是。`控制台` 的框 `[2378,43,55,27]` 里只有两种颜色：

| 颜色 | 像素数 |
|---|---|
| (236,234,228) 浅 | **421** |
| (26,25,23) 深（页面） | 403 |

浅色略多——但那浅色是**字**。`_dominant_color` 取最多的颜色当 `fillColor`，于是"字色"变成底色、"页面色"变成字色，正好反了。

字色为什么也反了？`_control_text_bbox` 把取色窗收缩到 `[2390,46,31,20]`（字的内部），`resolve_text_style` 用这个窗的**边框环**估计背景——环全是笔画，于是背景=字色、前景=页面色，又反一次。两次反转叠起来就是"浅底深字"。

另外放大 5 倍看参考图：`控制台` 外面**确实有一个圆角描边胶囊**（深底 + 约 1px 亮边）。所以正确的产物是"胶囊面板 + 透明控件 + 浅色文字"，三者缺一不可。

### 10.2 修法：`control_palette()`

一条判据：**控件内部最大单色占比 ≥55% 才算"自己拥有底色"**；否则它就是画在页面上的文字。

| 样本 | 内部主色占比 | 判定 |
|---|---|---|
| `控制台` | 0.33 | 无底色 |
| `社区` | 0.43 | 无底色 |
| `看详情` | 0.37 | 无底色 |
| `复制模型 ID` | 0.39 | 无底色 |
| `手动执行` / `刷新` | 0.85 / 0.83 | 有底色（蓝） |
| `搜索` | 0.77 | 有底色（蓝） |
| `展开查询` | 0.90 | 有底色（浅灰） |

- 有底色：`fillColor` = 该颜色（不是 `_dominant_color` 的整框众数）；
- 无底色：`fillColor = transparent`，`borderWidth = 0`——**描边归面板层**，否则胶囊会被画两遍；
- `textColor` = 内部与底色距离 ≥40 的最重颜色（不再用收缩窗的边框环）；
- 页面底色同理改用"元素之外还剩什么颜色"（§9.2），面板过滤也用它，避免把"页面色面板"当成面板。

### 10.3 一个必须更正的测量方法

`check_benchmark_families --rerun` 复制冻结 pipeline 后走 `--reuse-prepared`，**直接读回 `pipeline/12_design.json`**，不会调用编译器。所以：

- §9.4 的"三族零新增 panel"不是"规则没触发"，是**设计根本没重建**；
- 下游改动的确定性 A/B 应该是：读冻结的 `11_som.json` + `provenance.reference` → `build_image_design()` → 写回 `12_design.json` → `--reuse-prepared` 渲染并出 acceptance。这条路不重新采样 VLM，只让编译器改动生效。

## 12. `社区` 的 3px：一条凭空生成的边框（2026-11-12 02:00）

### 12.1 现象与错误归因

`控制台` 修好后，同帧的 `社区` 从 native pass 掉到 fail（`dx=dy=3`，`cov 0.711`）。第一反应是"去掉 1px 边框后文字框定位变了"——**错**。查证：

| 层 | before | after |
|---|---|---|
| 设计元素 | `x=1205 y=42 59×29` | **完全相同** |
| Figma TEXT 节点 | `1206.5,40 55×33 @27.5` | **完全相同**（只有 fills 差 1 个色阶） |
| 导出墨迹框 | `(1205,42,59,29)` | `(1207,45,54,26)` |

节点没动，墨迹却变了 3px —— 说明 before 的墨迹**根本不是文字**，是那条边框：它 59×29，正好等于参考文字的 60×29。

### 12.2 根因：`_contrast_border_color()` 会给不存在的边框编一个颜色

```python
def _contrast_border_color(fill):
    return "#c8d1de" if luminance >= 150 else "#64748b"   # Tailwind slate-500
```

`_sample_border_color()` 在参考图里找不到边框时，就返回这个默认值，于是**每个控件都被画上一条边框**。实测：

| 族 | 有边框的控件 | 其中边框色与参考图真实边色相差 ≥24 |
|---|---|---|
| dark | 10 | **5** |
| light-form | 13 | **4** |
| light-table | 13 | **12** |

这就是交接文档 §6.3 里"默认调色板"的真正含义——不是配色选错，是**凭空造了一条边**。

### 12.3 修法：`border_of()`

边框是**一个框**：距元素边缘 1px 的那条线上，至少三边颜色相同、且与填充色差 ≥16。只有一边不同的是字形触边或抗锯齿，不算边框。

| 样本 | 四边（内缩 1px） | 判定 |
|---|---|---|
| `自动备份`（light-form 输入框） | 四边全 `(192,200,216)` | 有边框 ✓ |
| `搜索`（light-table 蓝按钮） | 三边=填充，一边=白 | 无边框 |
| `社区`（dark 导航文字） | 四边=页面；只有底边是字形 | 无边框 |

修完：**dark 0/11、light-form 9/15、light-table 1/13** 保留边框（原来 10/10、13/13、13/13 里绝大多数是假的）。三条判据叠加才稳：

1. 距边缘 1px 与 0px 两条线都探（bbox 与真实边沿有 ±1px 抖动）；
2. 至少三边**同色**（单边不同 = 字形触边/抗锯齿）；
3. 边框色不能等于**外部环色**（那是 bbox 比按钮大、露出了页面）。

### 12.4 结果

三族 within30 **基本不变**：dark `94.65 → 94.62`、light-form `92.21 → 92.22`、light-table `95.27 → 96.26`——1px 的线在 30px 分块里几乎看不见。但产物层面是质的修正：`社区` 不再有一个参考图里不存在的框。剩下的差异就是字号/字重（第 5 项），见 `output/_p11_noborder/shequ_final.png`。

## 13. 第 5 项：字号（2026-11-12 03:00）

### 13.1 病灶：量具本身只有 1/6 分辨率

`ink-convergence` 从 2026-11-09 起只用**墨迹高度**做闭环：测参考图和渲染图的墨迹高，按比值缩字号。这个量具对小字是失效的。

一个 18px 字的墨迹高是 **17-19 px**，±1 px 就是 **±6%**，和被校正的误差同量级；而同一行的墨迹宽是 **72-140 px**，同样的 1 px 只有 **±1.4%**。更要命的是高度**看不见**「字号对、字距不对」——两者都表现为宽度偏差。

holdout 上这个误差是可见的：同一栏四个并列 label，字号分散在 **16.25 / 18 / 19.5 / 20.75**，而它们的参考墨迹高都只有 17-18 px。

| `访问环境验证` | 20.75 | 117×19 | 123×20 | **+6** |

### 13.2 参考侧的框不是紧框

宽度通道的第一版直接拿 `styleEvidence.ink_bbox` 当窗口，结果字号被放大到 24.5：

```
请求编号  ink_bbox = [272, 676, 328, 17]     # 四个字实际只占 72
```

`ink_bbox` 是**元素框**（这一格占满整列 334 px），不是墨迹框。它向右越进了 `当前队列位置`，把邻居的笔画算了进来。门禁的 `referenceInkBBox` 是紧的，但那是渲染之后的产物，校准阶段拿不到。

更麻烦的是这一格还带一条 `#cc` 左右的浅灰分隔线：它在 y 带上贯穿整个窗口，用 40 的对比度阈值会被当成墨迹。第一版用「从中心向两侧扩展到空白」的扫描法，又因为拉丁字母间距（5-8 px）比阈值宽而截断，`CONTENT REVIEW CENTER` 被量成 89 px。

### 13.3 修法：三道闸

`_text_run_width()`：

1. **阈值 60，不是 40**——单元格里 204 的浅灰条离页面只有 51，而页面上最浅的标签 `#818790` 离页面 122，60 能分开；再加「一列至少 2 个像素」挡掉抗锯齿碎点。
2. **先去掉贯穿的细带**（≤2 px 厚、覆盖 80% 宽/高），那是表格线，不是笔画。
3. **取最左的一段**——这些标签在框内左对齐，图标和下一格都在右边。窗口再用渲染墨迹宽的 2.4 倍封顶，因为渲染侧是 Figma 给的紧框，不会越界。

主循环里的决策：

- 只对**单行**用宽度（`ink_bbox` 高 ≤ 1.6×字号），多行文本的行长由断行位置决定，与字号无关。
- 宽度比超出 `[0.55, 1.8]` 直接跳过——那不是字号，是窗口里混进了第二个元素。
- **宽和高的方向相反就跳过**。`系统运行正常` 参考 128×17、渲染 123×19：源字形**更宽且更矮**，这是字族差异，按任何一个缩放都会让另一个更差。
- 高度通道保留原来的 `[0.85, 1.175]` 死区和 `[0.7, 1.5]` 钳位（§5.2 的两个数是有测量支撑的）；宽度通道自己的门槛是 4%。

顺带把 `type == "text"` 放宽成「有 text」：按钮标签也是 TEXT 节点，`ink_bbox` 是标签自己的框，此前整类控件被排除在字号校准之外（`检查状态` 因此一直停在 17）。

## 14. 第 6 项：字重（2026-11-12 05:00）

### 14.1 先更正 §13.5 的一个归因：控件底色是对的

§13.5 写「`检查状态` 的按钮参考是浅蓝底（153,176,228）、渲染是白底」。**这条是错的。**

实测这个按钮的底色：参考 `(255,255,255)`、渲染 `(252,252,252)`，差 3 个色阶。之前那个 `(153,176,228)` 来自「取文字窗口内所有像素的中位数」，而 72×18 的窗口里有四成是笔画和抗锯齿，中位数被拉到了文字色上。按窗口**边框**取（`_ink_extent` 一直是这么做的）就是白的。

底色、边框（参考有 1px `#dde3ea`、渲染没有）都是小差，不是 coverage 0.50 的原因。真正的原因是字重：参考是粗体，渲染是 Regular。

### 14.2 量具：`2 · 面积 / 周长`，不是面积

面积在这里不可用。`请求编号` 的参考墨迹面积比渲染多 **26%**，但两者笔画完全一样粗——差的只是文字颜色深浅（`#818790` 对更浅的灰）。面积统计的是「墨水量」，颜色也进这个数。

笔画用一个几何量：一笔宽 `w`、长 `L`，面积 `wL`、周长 `2L`，商 `2·面积/周长` 就是 `w`。字形当然不是一笔，但同一段文字在两个字重下**骨架相同**，所以两次测量的比值就是字重比。

holdout 上的分离度（参考 ÷ 渲染）：

| 文本 | 面积比 | 笔画比 | 肉眼 |
|---|---|---|---|
| `处理进度` | 1.55 | **1.47** | 参考明显更粗 |
| `检查状态` | 1.70 | **1.43** | 参考明显更粗 |
| `REQ-OIBFZVUES` | 1.54 | **1.54** | 参考明显更粗 |
| `请求编号` | 1.26 | **1.02** | 一样粗 |
| `预计等待时间` | 1.29 | **1.00** | 一样粗 |

笔画比把「粗」和「深」分开了，面积比没有。

### 14.3 为什么要单独占一轮渲染

字号和字重都改墨迹。如果在同一帧上量两个，每个校正都会把另一个的效果算进自己头上：字号缩 6% 会让面积掉 6%，字重再按掉下去的面积加粗，就是双重校正。

所以字重进一个独立的组 `font-tone`（产物目录 `figma_font_tone`），排在 `ink-convergence` 之后，读的是字号已经收敛的那一帧。没有调整时组不渲染，正常页面不多付一次成本。

判据（`calibrate_weight_from_render`）：

- 两侧墨迹高差 > 15% → 尺寸还没定，跳过（在错的尺寸上加粗是双重校正）；
- 笔画比落在 `[0.78, 1.22]` → 跳过；
- 步进 `(笔画比 − 1) / (0.44/300)`，即 400→700 对应 1.44。

`0.44/300` 是实测的：Noto Sans SC 的 stem 在 400 是 0.055 em、700 是 0.078 em，300 档换 44%。只用了斜率，换字体要重读这两个数，不是换一套模型。

### 14.4 拉丁字母加粗会变宽，CJK 不会

CJK 是等宽的，加粗不改 advance：`处理进度` 400→700，Figma 节点宽 **78→78**。

拉丁不是：`REQ-OIBFZVUES` 在 400 时 140 px，被推到 800 后变成 **184 px**，而参考是 172。加粗把它从「窄 32」翻成「宽 12」，亲手制造了一个新的 size fail。

所以拉丁文本的步进上限收到 300（一次一档），CJK 仍可一次跨两档。
