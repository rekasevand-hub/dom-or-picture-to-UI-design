## 2. 分类顺序（这就是那条被认可的补丁规则）

1. 四维全过 → `pass`
2. **未贴边的轴上有位移** → `mechanical`
3. **只有贴边轴上有位移** → `instrument-capped`
4. 宽超、高在容差内、**横向未贴边** → `typeface-advance`
5. 尺寸失败且至少一个未贴边轴 → `mechanical`
6. 几何全过、只有 coverage/edgeF1 差 → `typeface-glyph`

第 2 条排在第 4 条前面，是这条规则的关键。`REQ-OIBFZVUES`（宽 +6、高 +2、位移 0）
落 `typeface-advance`；`系统运行正常`（宽 −5、高 +2、**dy −6**）落 `mechanical`。
两者形状一样，差别只有一个：**位移是否干净**。只看「高宽不自洽」会把 13px 的间距缺陷
放进「不挡发布」那一层——这正是补丁规则必须先看位移的原因。

## 7. 「机械 28」这个数，到 16:15 才真的能用

上表 28 条机械失败里，**有 7 条参考读数是坏的**——不是「差得多」，是「量的对象错了」：

| owner | 读数 | 真正量到的 |
|---|---|---|
| `¥20.24`（dark） | 参考宽 **278** = 整个窗口 | 正文 + 右边 `起 ¥23.0` |
| `¥1.16`（dark） | 223 | 正文 + 邻居 |
| `AtomCode`（atomgit） | 172 | 正文 + 右侧标签（我们的渲染只有 88） |
| `Nex-N2.6`（atomgit） | 参考与渲染**零重叠**（cov 0.00） | 配对就错了 |
| `从 Meta 内部走出来的…` | 560 | 正文 + 邻居 |
| `TOPI` / `like` ×3 / `Java` / `10条/` | 比渲染宽 1.6–2.1 倍 | 同上 |

根因是**断字阈值不可能同时成立**：

```
¥20.24      字号 47px，与邻居间隔 21px = 0.45em   → 1.0em 阈值把它并进来
CONTENT SECURITY  字号 18px，两个词间隔 13px = 0.72em → 0.35em 阈值把它切开
```

邻居间隔（0.45em）比词间隔（0.72em）还小，**任何单一 em 阈值都会在一边出错**。
所以判据换成宽度先验：参考宽超过「我们自己的渲染宽 × 1.6」就是读数不可信，
从合并段的**两端**裁掉（不许从中间抠，避免切出单个字形）。

落地后（`REFERENCE_WIDTH_RATIO_MAX`，只读探针实测）：

| 项 | 结果 |
|---|---|
| 参考读数变化 | **10 条**，全部向 0 靠近：`¥20.24` wd −133→**−9**、`¥1.16` −111→**−18**、`从 Meta…` −295→**+6**、`like` ×3 −27→**+3**、`10条/` −32→**−3** |
| 状态翻转 | **0** |
| 门禁通过数 | **111 → 111**（五族一个没动） |
| 仍超可信上限（>1.6） | **7 → 0** |
| 反向可疑（<0.6） | **1**（`项目名称`：参考 89、我们 195），已标 `referenceWidthSuspect`，只记账 |

**所以「机械 28」这个数字没变，但它的含义变了**：之前是 21 条真机械 + 7 条坏读数，
现在是 28 条都能当判据用。这也解释了为什么修完一分没涨——修的是尺子，不是这一页。
