R2-Q02 单子项容器与冗余 layoutMode
已知事实
URL 自主截图版的220个Auto Layout Frame中：
133个有至少两个在流子项。
43个只有一个在流子项。
44个没有在流子项，子项为ABSOLUTE。
例子：
读书网标志，1:368：270×60裁剪窗口，唯一子项是1440×2550绝对图片。
京东图书活动、书单馆、当当图书活动：190×100裁剪窗口，唯一子项是绝对大图。
搜索按钮，1:372：单子项，用于居中放置24×24搜索图标。
为什么问
V1目前采用“成员≥2”才建Frame的规则，可能漏掉有对齐价值的单子项容器；另一方面，纯裁剪容器保留layoutMode没有排版职责，需要可执行的保留、移除规则。

请导师回答
单子项什么时候保留layoutMode？
只有绝对图片的裁剪容器是否移除？
唯一子项是flow容器，父级是否也需要stack？
决策记录在哪里，字段是什么？
无法判断时默认保留还是移除？
回答位
本次实际做法
沿用题内统计：43个单在流子项容器与44个零在流子项裁剪容器承担不同职责。

R1抽查证明裁剪窗口的唯一大图为绝对定位；没有执行移除布局后的对比实验。

通用建议
1. 分开决定“保留Frame”和“保留layoutMode”
一个裁剪窗口即使移除Auto Layout，也仍应保留Frame与裁剪能力。

不能把“移除布局设置”等同于“删除容器”。

2. 有布局职责的单子项保留
需要下列任一明确职责时，可保留：

居中、贴边等对齐。
padding。
Hug内容尺寸。
Fill可替换槽位。
需要尺寸变化后仍维持的布局关系。
记录具体行为，不以“以后可能有用”作为唯一理由。

固定24×24图标居中于可变按钮是正例。

3. 纯裁剪、零在流子项
新建时默认普通Frame。
已有节点列为移除layoutMode的候选。
移除前后需要保留并核对：

容器尺寸。
裁剪。
图片偏移。
外层占位及参与方式。
父级Hug/Fill、最小尺寸耦合未弄清时，不立即移除。

4. 子容器是flow，不代表父也必须flow
父只做坐标或裁剪边界：可以普通Frame。
父需要padding、对齐、宽度填充或随子项增高：需要相应布局。
尺寸变化只有跨越每层尺寸依赖，才能向外传播。

普通Frame＋固定高度，不会自动包住变高的内层flow。

5. 未知时不做破坏性优化
已有稿：默认保留当前结构，标记unknown。
新建稿：保留语义Frame，但不凭空开启stack；先用固定几何，等待核对。
未知项不自动进入true flow。

6. 决策存储
IR作为策略事实源，manifest记录输出和验证结果，图层名只做人类识别。

建议字段：

字段	含义
container_key	容器稳定语义键
role	语义角色
in_flow_count	在流子项数
absolute_count	绝对子项数
layout_required	是否需要布局
layout_purpose	布局职责
sizing_dependency	尺寸依赖
clip_required	是否需要裁剪
decision	保留、移除候选、固定保留等
evidence	决策证据
confidence	已测、推断、未知
verification	验证状态
output_node_ref	当前输出节点引用
layout_purpose 至少区分：

arrange
align
padding
content-sizing
clip-only
依据 / 可复现证据
建议实验：

按钮变宽，图标仍应居中。
替换大图，裁剪窗口外部占位不变。
内层内容增高40，检查父高度是否按预期增长。
三项对应不同职责，不能用“成员≥2”统一判断。

不确定项
学生V1具体实现未审查；已有43个单在流子项容器并非全部验证过对齐、padding和内容适应。

失败或放弃的方案
无历史删除失败记录。

不建议：

单子项全部扁平化。
裁剪容器全部开启flow。
我的备注
节点名、节点内附属信息，都不应成为唯一策略存储。

当前环境不保证支持节点内写入自定义数据；2.0应将外部可导出的IR/manifest作为必需项。

2. normal保留normal，测量与估算分开

3. 四项独立验收
以下是起始阈值，不是普适定律：

项目	起始判据

换行	未改内容、宽度时，行数和换行点一致
可见字形	可见边缘偏移≤1 CSS px作为几何检查起点，另核对字形特征
截图、画布缩放需要换算。

拿不到基线时，标unknown/not-evaluated，不能填0误差。

抗锯齿、hinting和色彩会影响像素差；跨渲染器不设置未经标定的统一像素通过率。

字体相同也不保证逐像素相同。
