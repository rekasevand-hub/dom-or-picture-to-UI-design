R1-Q01 三块画板是否来自同一套生成流程？
已知事实

三块画板在同一份 .fig 中，但结构差异很大：
DOM 版：125 个 Frame，只有 1 个 stackMode，166 个 Text，24 张唯一原图。

R1-Q02 URL 自主截图版的 220 个 stackMode 是真布局还是结构标记？
已知事实

220 个 Frame 带 stackMode。
其中 133 个有不止一个子节点，87 个只有 1 个子节点。
44 个子节点带 stackPositioning=ABSOLUTE。
144 个子节点带 stackChildAlignSelf=STRETCH。
45 个子节点带 stackChildPrimaryGrow=1。
stackSpacing 既有 null（151 个），也有 6（37 个）、16（11 个）、10（5 个）等非零值。
为什么问
“开了 Auto Layout”不等于“真的会流式重排”。我们需要知道哪些容器是真实布局、哪些只是结构标记，才能设计安全的 flow 候选条件。

请导师回答

本次实际做法：这 220 个 stackMode 中，哪些是真流式布局，哪些只是结构标记？

“真流式 / 结构标记”二分不够准确。应至少分为：①多个在流子项参与排列；②单个在流子项，仍可提供居中、内边距和内容适应；③零个在流子项，仅用于裁剪或叠放。
本次补查结果：包含根容器的 220 个 Auto Layout Frame 中，133 个有至少两个在流子项、43 个有一个在流子项、44 个没有在流子项。与题内按“全部子项数”分类的 133/87 对应；后者的 87 个单子项容器里，有 44 个子项实际是 ABSOLUTE。
第一类有真实排列约束，但是否满足内容变化后的设计意图仍待测试。第二类不能简单称“假布局”。第三类虽开启布局，但不承担子项之间的流式排列，可列为移除冗余布局设置的候选。

你如何判断一个容器是否应该开启 Auto Layout？

通常看是否存在可表达的排列、对齐、间隔、内边距或内容驱动尺寸关系，而不是只看命名或子项数量。2.0 的具体准入条件见 Q03。
如果子项内容高度变化，哪些容器会重排，哪些不会？

纵向流会依据直接在流子项的实际高度重新排列后续兄弟；但文字变化只有在改变了其所在直接子项高度时，才能继续向外传播。固定高度卡片里的文字增长可能只是溢出或被裁切。
中的某一直接栏目实际增高后，后续栏目会下移，Hug 父容器增高。
也为 Hug 高度，可继续向外传播。
横向 Auto Layout 不等于纵向响应式重排；固定高度与未开启换行仍可能导致溢出。绝对子项不挤开兄弟，也不贡献正常流尺寸。
打开布局后是否遇到过位置漂移？如果有，具体表现是什么？

无法确认历史上是否发生以及具体表现。当前最终状态不足以证明“曾漂移又修复”。可预期风险包括字宽变化、Fill 重分配、居中基准变化、间距取整等，属于待验证风险而非本次失败记录。
通用建议：

分别记录在流子项数、绝对子项数、尺寸策略、对齐与换行。stackSpacing=null 仅表示该导出字段未显式给值，不能据此认定布局无效；应结合运行时属性或可靠默认值。
将“设置为 Auto Layout”“布局引擎实际参与”“扰动后行为正确”分成三级验收，不用 stackMode 数量作为结构质量分数。

R1-Q03 DOM 版为什么只开最外层 Auto Layout？
已知事实

DOM 版有 125 个 Frame，只有外层 1 个 stackMode。
外层 11 个直接子项参与排列；其余 124 个 Frame 内部保持固定坐标。
外层没有写入 spacing/padding/align 字段，按默认值处理。
11 个子项高度合计 2545，正好等于外层高度。
为什么问
这是我们和导师最直接可比的结构差异。我们需要知道它是“主动选择”还是“失败后的退路”，以及内部 Auto Layout 的真实失败模式。

请导师回答

本次实际做法：为什么内部栏目、卡片没有开启 Auto Layout？

当时具体选择原因无法确认。已核实的结果是：外层纵向 Auto Layout、11 个固定尺寸在流子项，内部 124 个 Frame 依赖局部坐标。该结构适合保存固定视口的一帧几何，但“适合”不是历史动机的证据。
不能声称 DOM 自动转换了完整布局；本次只是 DOM 测量支持的几何重建。
是否尝试过内部 Auto Layout？失败的具体表现是什么（位置漂移、尺寸变化、换行、绝对覆盖、子节点数量不匹配等）？

无法确认。没有可核实的前后状态和失败记录，不能把当前固定坐标解释为失败后的退路。
你会用什么条件判断一个容器可以安全开启 Auto Layout？

建议 2.0 栏目级 flow 候选条件：
语义上有明确先后顺序。
在流内容沿单一主轴排列，重叠只属于可单独识别的背景/装饰。
父子关系、有效内容数量和视觉顺序一致。
间隔、内边距、对齐及尺寸策略可明确表达。
字体、文字宽度与素材尺寸已稳定。
无 Hug 依赖 Fill、Fill 又依赖 Hug 的未解尺寸循环。
能明确说明内容增高后哪些兄弟应该移动。
网格或多列需要先建立“行/列/侧栏”层，再验证每层；不要将所有后代一次塞进一个线性布局。像素级共享边框、负间距、叠放等不能表达或验证失败时，保留最小固定坐标区域，并记录原因。
内部固定坐标规则：所有位置均以所在固定容器为坐标系；记录容器矩形、子项局部矩形、裁剪范围与锚点；只将装饰和叠放子项排除在流外，不将主体文字偷偷移到绝对定位以掩盖布局错误。
如果开启后位置漂移，你建议如何回退？

在副本中转换；转换前保存父子层级、顺序、尺寸、变换、约束、裁剪及文字排版参数。先固定新布局的外部矩形，再由内到外、逐层启用。
验收不通过时优先保留原子树、丢弃候选子树，而非反复修补已漂移坐标。若必须原位恢复，应关闭布局并恢复原层级、局部矩形及相关属性；有旋转/嵌套缩放时需要变换矩阵换算，不能仅做坐标相减。
从无旋转、无缩放的全局 DOM 矩形转成局部坐标时，使用 子项左上角 - 父容器左上角，并统一滚动偏移、边框基准与 CSS px 尺度。不同坐标系不能直接混用。
如果没有自动回退，你如何保证开启布局后的外观不漂移？

不能仅靠开启前的判断保证。必须在测试副本对比实际排版结果；没有验证能力时，保留原稿并把候选标为未验收，不宣布转换成功。
建议固定视口验收：关键容器和文字框边界误差不超过 1 CSS px；截图缩放比例为 s 时，相应画布阈值为 s px；换行行数、内容数量、显示状态必须一致。图片保留纵横比，不以平均误差掩盖少量大偏移。文字基线与可见字形另做检查，边界框一致不代表字形一致。
内容测试：某在流栏目实际增高 40 CSS px 后，预期下游偏移为 40；另测试标题变长和宽度 ±10%。这些是建议的测试输入，不是原站响应式要求。
通用建议：

先固定参考几何，再推断约束，最后用扰动实验判定约束是否成立。原稿、候选稿、验收结论分离；不要把“能看起来一样”当作“布局规则正确”。
依据 / 可复现证据：

当前 DOM 根容器 VERTICAL/FIXED×FIXED、间距/内边距 0、11 个在流子项、无绝对子项；直接子项高度合计 2545。其余 Frame 未开启布局。
反例：直接将一个固定 237 高的卡片中文字加长，不保证栏目增高；固定卡片高度阻断尺寸传播。
不确定项：内部布局是否尝试过、是否有自动回退机制及历史误差数值；无法确认。

失败或放弃的方案：无本次历史失败可引用。2.0 不采用“批量开启所有容器、之后肉眼修补”的方案。

R1-Q04 空白间隔 Frame 是否是推荐模式？
已知事实

DOM 版外层 11 个直接子项中，6 个是内容 Frame，5 个是空白间隔 Frame。
间隔分别是：焦点前 20、栏目前 20×3、页脚前 50。
外层 spacing/padding 为默认 0，栏目间距完全由空白 Frame 撑开。
为什么问
这直接影响我们 2.0 是采用 itemSpacing/padding 还是保留 spacer 节点。两种做法对可维护性、响应式和后续编辑影响不同。

请导师回答

本次实际做法：空白间隔 Frame 是有意设计，还是工具链自然结果？

gap/padding 优点：层级干净、增删栏目方便、间隔不易被误选；缺点：单一 gap 无法表达任意不同间距，可能需要额外但有职责的容器。

你建议的统一层级是什么？页面 → 独立栏目 → 列表/卡片 → 图片、标题、作者 是否足够？

作为最低规范足够，建议扩展为：页面 → 页面区域 → 独立栏目 → 内容集合/布局行列 → 重复卡片 → 内容元素。不是每个节点必须经过全部层级；无职责的空层应省略。

什么时候用 Frame，什么时候用 Group？什么时候需要额外 wrapper？

Frame：需要明确尺寸、背景、边框、裁剪、布局或约束时使用。Group：仅需一起选择/移动且没有独立布局与裁剪职责时使用，不作为未来布局容器的替代。
wrapper 仅在承担具体职责时存在：控制列宽、行列排列、素材裁剪、对齐槽位或独立变换。单子项 wrapper 可以合理；不能只因“层级看起来整齐”而新增。
布局与裁剪职责宜分离，例如封面槽位控制对齐，内部图片控制裁切；若一个 Frame 已可清晰承担二者，则不强制再套一层。
页头、焦点区、页脚、浏览器滚动条应如何独立或合并？

页头、焦点区、主内容、页脚各自独立；页头内部可分工具栏/品牌搜索/导航，焦点内部可分轮播/广告/分类。
浏览器滚动条不属于网页业务内容。若任务要求复现整张截图，放在独立“截图外观层/浏览器界面”中，排除在网页内容 flow 之外；若目标是网页设计稿，不包含浏览器界面。用户上传图中的元素不能在未说明时静默删除。
命名有没有推荐规则（中文语义名、英文标识、序号、节点 ID）？
